# Remote Agent for macOS

The Mac client for rad, written in Rust with [GPUI](https://gpui.rs), Zed's GPU-accelerated UI framework, and [GPUI Kit](https://gpui-kit.com)'s components. It replaced the SwiftUI Mac app that `apple/` used to build, and keeps its release feed, so that app's copies update to it.

## What it does

It does what the iPad app and the other clients do, with the gaps listed below.

- **Pairing:** paste the link `rad pair --print-url` prints, or pass it on the command line. Settings › Servers reconnects, removes (unpairs) and adds servers.
- **Install on a server over SSH:** the pairing page also takes an ssh host (`user@host`, or a `Host` from `~/.ssh/config`; `ssh <host>` must work without a password) and lists the steps as it goes (`src/store/ssh_install.rs`). A server without rad (on its login shell's PATH or in `~/.local/bin`) gets the latest release for its OS and CPU (Linux or macOS, x86-64 or arm64), downloaded on this Mac, checked against the release's `SHA256SUMS` and unpacked into the server's `~/.local/bin`. Unless rad already answers there, `rad install-service` starts it, with the login shell's PATH so that it finds the agents. On Linux it turns on lingering first where it can without a password (`sudo -n`); otherwise it says to run `sudo loginctl enable-linger <user>`, since systemd would stop rad when the ssh session ends. Then it pairs, at the link's addresses (loopback left out) and then the address ssh connects to (`ssh -G`). A host never seen before is trusted the first time (`StrictHostKeyChecking=accept-new`). `RA_GPUI_SSH` names a stand-in for `/usr/bin/ssh`, for testing.
- **The sidebar:** Inbox (Needs You, Recent, Archived, Servers), Projects (each server's projects, under a badge with their initial, with their sessions; with one server, no server heading), Columns (Needs You, Running, All Sessions, each project and the archive, beside their sessions) or All Projects, which only this client has: every server's projects in one list, the one with the latest session first, each with its server's name beside its own when there are several, then the Inbox's Archived and Servers. View › as Inbox, as Projects, as Columns, as All Projects (⌘1–4). A session's row shows its branch, its agent and its server, and, where it isn't under its project's heading, its project's badge in front, with its state as a dot under the badge or a ring around it (Settings › General › Sidebar › Session state); hovering it shows a card with its project, server, branch, model and context, and turns its age into ✓, which archives it at once. Right-click a session to rename, archive, unarchive or delete it, a server for New Session, Reconnect, Server Settings and Remove, a project for New Session and Forget Project. "Archive old sessions" archives what had nothing new for a week. A session at work pulses in the lists. View › Show or Hide Sidebar (⌃⌘S), or the button beside the traffic lights, hides the sidebar (and the Columns layout's middle column) to leave the session the window.
- **The window:** it has no title bar of its own. Each column's bar is at its top: the sidebar's with the layout's name and its buttons, the session's with its title. Drag any of them to move the window.
- **Search (⇧⌘F):** every connected server's sessions, merged round-robin, with snippets; a result opens its session at the item, which lights up for a moment. **Find in the session (⌘F, ⌘G, ⇧⌘G)** over the transcript, in a field at its top right, opening the run that holds the match.
- **A session:** its transcript, with runs of tool calls folded into one row ("Ran 4 commands, edited 3 files"); an open run's steps hang from a rail under it. A tool call opens to its command (when its row doesn't already show it whole), edit, new content or input, and its output (30 lines, then "Show all"). Sub-agents' steps sit in their tool call. Replies are Markdown, with raw HTML kept as text, a code block's language and Copy in its corner, and their `rad-image:` pictures, the prompts' and the tools' images in a viewer. The foot shows what runs in the background and a session's error; a turn that failed says why once, in its error.
- **The session's bar:** "project / title"; its state, Failed after a turn that failed; and buttons for Changes (with the lines the session added and removed), Commit… and the Terminal. A narrow window drops the project and the state's name first, then the buttons, which the ⋯ menu has too.
- **The ⋯ menu:** Permissions, Find, Changes, Commit…, Terminal, Rename…, Fork…, Archive…, Delete…, with their shortcuts, the project and branch, and Force stop while it runs. The Session menu has them too (⌥⌘C commits).
- **Approvals:** tool approvals (Deny asks for a reason), plans, and questions with their options and an answer in your own words. The card stands for the tool call it asks about, with its buttons under what they answer.
- **The composer:** the prompt box a new session has too (`ui/prompt_box.rs`): the + menu, the agent with its model and effort, dictation and Send in the box, and under it the server, the checkout or worktree, the branch, the context used and the permissions. What a session can't change once started is greyed out; the permissions stay a menu. Return sends, Shift-Return starts a new line, ⇧⌘Return steers into the running turn for agents that take it. Slash commands are suggested as you type `/`. Images attach from Files…, ⌘V, Paste Image or a drop, scaled to 2048 px and uploaded at once. Queued prompts have Send now, Steer and Cancel; Stop (⌘.) interrupts. Save as Draft (⌘S) and a session's draft (Edit, Send). Sending to an archived session offers to unarchive it. A prompt you haven't sent stays for the next launch. Dictation, in the app bundle.
- **Changes:** the session's diff or a turn's, with the files on the left and the chosen file's diff beside them (in a narrow window, the list and then the diff), and Revert files… to before a turn in a worktree.
- **Commit:** the preview, the message, Commit, Commit & push, or Commit, push & open PR, and the steps as rad runs them, in a dialog as tall as what it shows.
- **Fork:** after which turn, the agent and its options, the project folder, a new worktree or this session's.
- **The terminal (⌘J):** the session's shell on the server, instead of the messages, below them or beside them, with copy on select. Hiding it leaves the shell running; it resumes where it left off.
- **New sessions (⌘N):** "What should we build in *project*?" over the prompt box. The bar's project menu picks the project, adds a folder as one, or forgets it. The agent pill's menu has the agents (those that aren't signed in or installed greyed out, with why), the usage gauge, the model and the effort; the pickers under the box, the server, where it works (the checkout, a new worktree or an existing one), a new worktree's branch (named, or rad's name, or one not checked out) and base, and the permissions. Save as Draft and "Continue a terminal session…" are in the + menu. Return starts. It starts with the server's default agent, else the one used last, and Esc goes back to the session that was open.
- **Settings (⌘,):** as T3 Code lays them out: a sidebar of categories with a search field (General, Appearance, Chat, Terminal, and each server), and the chosen one's page of grouped rows, each with what it does: theme, the interface's text size, the messages' font and size, the code font and code size (replies' code, tool calls, diffs and the terminal, which refits its rows and columns), grouping of tool calls, limiting the prompt box's width (to 1,120 points, a 13-inch laptop's, centred in a wider window; off, it's as wide as the window) and, separately, the messages' width (the same column), the sidebar layout and how a session row shows its state, where the terminal opens, notifications; and each server's settings: rad's version and update, the agents with their versions, usage limits, Sign In and Update (with the sign-in page and its code), and the default and system agents.
- **Notifications:** when a session needs you, finishes or fails and the window doesn't show it; clicking one opens the session.
- **The Dock icon** (Settings › General › Dock, both off by default): a badge with the number of sessions on every server that wait for an answer, failed or have a reply you haven't read; and a bounce, once, when a session needs you, finishes or fails while another app is in front, or, with "Keep bouncing when stuck", until you come back or no waiting or failed session needs you any more. macOS draws the badge only when the app may show notifications with badges, so the app asks for them at launch, and Settings says when System Settings holds them back (`store/dock.rs`, `ui/dock.rs`).
- **Unread state, connections, appearance:** a session is marked read while it shows in the window in front; the client reconnects with backoff and resubscribes from where it left off; Catppuccin, Frappé when dark and Latte when light. The sidebar and the Columns layout's middle column resize by dragging their right edge (a double click restores them), and keep their widths: the session list is as wide in every layout, as the sidebar or as the Columns layout's middle column, and that layout's first column, the servers and their projects, has a width of its own. The window reopens where it was, on the same display while it's connected (else kept on the main one), and in full screen if it was.

- **Pull requests:** rad finds the pull request from a session's branch on GitHub. Its row shows its number after the branch, with a glyph and colour for its state (open green, draft grey, merged mauve, closed red), and its hover card the title and where it stands ("Open · Checks failing · Changes requested", `store/pull_request.rs`). The session's bar has it as a button, with a mark for its checks (a green ✓, a red ✕, a yellow dot while they run): a click opens it in the browser, its tooltip says where it stands, and right-click or the ⋯ menu has Open on GitHub and Copy Link.

- **Updates:** the release build updates itself with Sparkle, as the SwiftUI Mac app did: once a day, or Remote Agent › Check for Updates…, from the latest release's `Remote-Agent-macOS-appcast.xml`; Settings › General › Updates turns the daily check and installing by itself on and off (`src/ui/sparkle.rs`). The development build updates from the Mac that builds it, over ssh (see below).

Not yet: the Photo Library. The fonts are installed families only: GPUI loads a font by family name, so the system font's other designs (New York, SF Pro Rounded, SF Mono) aren't offered, and code is Menlo unless you pick another. Notifications reach Notification Center only from the app bundle; a bare build shows them in the window. The terminal draws with the code font, at the code size; Menlo lacks Nerd Font glyphs, so pick a Nerd Font there for them.

## Building and running

It needs Rust (stable, edition 2024), Xcode's Metal toolchain, which GPUI uses to compile its shaders, and an Apple Development certificate in your login keychain (Xcode › Settings › Accounts › Manage Certificates).

```bash
cd gpui
scripts/bundle.sh                                  # target/release/Remote Agent Dev.app, and /Applications
scripts/bundle.sh --release 0.12.0                 # target/release/Remote Agent.app, as a release
cargo run --release                                # or run it from cargo
cargo run --release -- "$(rad pair --print-url)"   # pairs at launch
cargo test
```

- **Two apps:** `scripts/bundle.sh` builds one of two apps, which sit side by side in /Applications (`src/store/identity.rs`):
  - **Remote Agent Dev** (`dev.remote-agent.gpui`), the development build, which `cargo run`'s builds are too. Its servers are in `~/Library/Application Support/Remote Agent GPUI/servers.json` (0600), without the tokens, which are generic passwords for the Keychain service `dev.remote-agent.gpui`, one per server id. It pairs as "Remote Agent Dev on <host>".
  - **Remote Agent** (`dev.remote-agent.app`), the release build, which the release workflow builds with `--release <version>` and signs with Developer ID, with the hardened runtime (`scripts/release.entitlements`). With a version it embeds Sparkle (`scripts/sparkle.sh` downloads it, pinned and checked) and its feed; without one it doesn't update. Its servers are in `~/Library/Application Support/dev.remote-agent.app`, its tokens under the service `dev.remote-agent.app`, so it never shares a pairing with the development build. `RA_BUNDLE_ID` gives it another bundle ID, and its own servers, for trying updates; `SPARKLE_PUBLIC_KEY`, a scratch key.
- **The app:** Open it from Finder. Double-click the app, not `target/release/remote-agent-gpui`: Finder opens a bare executable in Terminal. Pass a pairing link with `open "target/release/Remote Agent Dev.app" --args "$(rad pair --print-url)"`.
- **/Applications:** `bundle.sh` installs the development build in `/Applications` (`RA_GPUI_INSTALL_DIR` names another folder, or none when empty), so every worktree's build lands in the same place. The release build goes only where `RA_GPUI_INSTALL_DIR` says.
- **Updating another Mac with the development build:** it offers Remote Agent › Check for Update… (and the same in Settings › Updates). It asks once for the ssh host of the Mac that builds it (`ssh <host>` must work without a password), reads the `Contents/Resources/build.json` (the commit, branch and build time `bundle.sh` writes) of that Mac's Remote Agent Dev.app in the folder this app is in (else of the app at this one's own path), and on Install and Restart pulls that bundle with tar over ssh, checks that it's signed as the running app is (`codesign -R` with its designated requirement), quits, and a small helper swaps it in under the host's name for it, removing this one if its name was older, and opens it (`src/store/build_update.rs`). The app must run from a folder you can write to, and not translocated. `cargo run`, bare builds and the release build have no `build.json`, so they don't offer it.
- **Trying Sparkle updates:** build two release apps under a test bundle ID with a scratch key pair (CryptoKit's `Curve25519.Signing.PrivateKey`; the private key is its `rawRepresentation` in base64): `RA_BUNDLE_ID=dev.remote-agent.updatetest SPARKLE_PUBLIC_KEY=<public> RA_GPUI_INSTALL_DIR=<dir> scripts/bundle.sh --release 0.0.1`, then `0.0.2` into another folder. Zip the newer with `ditto -c -k --keepParent`, write its feed with `SIGN_UPDATE=$(scripts/sparkle.sh)/bin/sign_update SPARKLE_PRIVATE_KEY=<private> ../apple/scripts/appcast.sh <app> <zip> <zip url> <page url>`, serve both on 127.0.0.1, and open the older with `--args -SUFeedURL http://127.0.0.1:<port>/<feed>`. Sparkle relaunches the new one without `RA_GPUI_HOME`; delete `~/Library/Application Support/<test id>`, `~/Library/Caches/<test id>` and `defaults delete <test id>` afterwards.
- **Signing:** `cargo run` signs the app before it runs it (`.cargo/config.toml` makes `scripts/run-signed.sh` its runner), and `bundle.sh` signs the bundle. Both use your Apple Development identity, or the one `RA_GPUI_SIGN_IDENTITY` names; a bare build gets the identifier `dev.remote-agent.gpui`, so the development bundle and `cargo run`'s builds share their tokens. To run a bare build some other way, sign it first: `scripts/sign.sh target/release/remote-agent-gpui`.
- **Why it's signed:** the device tokens live in your login keychain. macOS lets a new build read, replace and delete the items an earlier build saved without asking only when both are signed with the same Apple-issued certificate (a Team ID). An ad hoc or self-signed build is a new app each time, and macOS asks for your login password. Without an Apple Development identity, `sign.sh` signs ad hoc and says so.
- **`RA_GPUI_HOME`:** keeps the servers file in another folder, such as a scratch one for testing. Its tokens get a service of their own, `<service> (<folder>)`, so they never mix with yours.
- **`RA_GPUI_APPEARANCE=light|dark`:** tries a theme without changing the Mac's appearance.

## How it's laid out

| File | What it holds |
|---|---|
| `src/protocol.rs` | The wire types. Enums are open, unknown fields are ignored, and the tests decode `protocol/fixtures`. |
| `src/images.rs` | Uploading and fetching images (`/v1/images`), scaled for agents, and cached on disk and in memory. |
| `src/net.rs` | The socket to one rad. It runs on a tokio runtime of its own, reconnects, and matches responses to requests. The UI gets what it hears over a channel. |
| `src/store/` | The client logic, free of UI and ported from RAKit: the streams' sync rules (`sync.rs`), the index and sessions, tool runs (with the shared test vectors), the sidebar's layouts and collections, search, find and slash commands (`search.rs`), usage limits (`limits.rs`, with the shared vectors), commit scopes, alerts, the app's prefs (`prefs.rs`), the saved servers, and their tokens in the Keychain (`tokens.rs`; tests use an in-memory store). |
| `src/store/ssh.rs`, `ssh_install.rs` | Running commands over ssh (for Check for Update too), and installing rad on a server and pairing with it. |
| `src/store/identity.rs` | Which app this is, the release build or Remote Agent Dev, and so where its servers and tokens live. |
| `scripts/` | `bundle.sh` builds the signed app bundle, the development or the release one; `sign.sh` signs a build; `run-signed.sh` is cargo's runner, which signs the app and runs it; `sparkle.sh` fetches Sparkle for a release build. |
| `src/conn.rs` | A GPUI entity per server: it applies events to the stores, and subscribes to a session while a view shows it. |
| `src/ui/` | The window (`app.rs`, `sidebar.rs`), the session (`session/`: its state, transcript, composer and header), the terminal (`terminal.rs`, alacritty's emulator on its own socket), the dialogs (`diff.rs`, `commit.rs`, `fork.rs`, `settings.rs`, `server_settings.rs`, `viewer.rs`), the new session form with its folder browser and import, the shared agent picker, task progress, and the palette. `assets/theme.json` holds the kit's theme, in the same colours. |

GPUI Kit pins its own GPUI snapshot (the `gpui-pre` crate), so `Cargo.toml` pins `gpui-kit` exactly. Bump them together.
